## 结论

NUCtool 的成熟度瓶颈目前不是缺少控制项，而是“用户点了什么、实际改了什么、哪个控制器改的、是否读回确认”还没有保持一致。第一阶段应先修正控制边界和状态语义，再投入新功能：性能档直连 NUCtool.dll；EC 只负责风扇；基准是独立 DLL 功能；DLL 厂商计划与 Windows 电源计划分开命名。

代码静态核对发现多处与已确认方向不符的实现或文案。它们可能导致用户误以为控制已经生效，或一次操作改变多个意料之外的参数。以下是审计发现，不代表已经在实机观察到硬件变化。

### 本次实施状态

- 已将 EC 风扇预设改为静音 / 均衡 / 散热优先曲线；选择曲线不再调用 DLL。
- 性能按钮现在调用 profile-only 命令，并在 DLL 调用后立即读取当前 profile 索引；只有索引匹配才标记为已验证。
- 基准改为独立开关：启用时请求 DLL benchmark flag 和厂商计划 4；关闭时按用户确认仅清除 flag，保留计划 4。没有 benchmark/计划硬件回读，UI 明示为最近请求。
- DLL 厂商计划不再称为 Windows 计划；无回读的 profile 请求、基准状态和计划状态不再使用默认值冒充实际状态。
- Rust 后端会把历史保存的 gaming/performance/benchmark EC 模式安全迁移为 custom，并在启动、更新、哨兵重启入口归一化，防止旧配置启动 EC benchmark fan mode。
- 已通过前端生产构建和 Windows 本机 Rust 单元测试；尚未在目标 NUC 上实测 DLL/EC 行为，也尚未完成安装包验证。历史 TDP/PowerShell/RGB/等待问题未在此轮重新复现。

### 建议本轮前三个产品任务

1. 统一控制契约：EC 风扇、DLL profile、DLL benchmark、DLL vendor plan、Windows 计划、EC TDP 各自单独命名和调用。
2. 建立状态契约：硬件读回、最近请求、未知/不可用、部分失败分别建模。
3. 改正电源计划和复合操作的命名/影响范围，禁止一个“模式”暗中跨写多个控制器。

## 3. PRD：核心控制可信度与状态可见性

### 1. 摘要

让 NUCtool 用户可以清楚、安全地控制设备性能和风扇，并知道每次操作具体由谁执行、改了什么、是否被硬件确认。本项目优先纠正 EC、NUCtool.dll、Windows 和旧 SDK 之间的边界与结果展示，再优化错误恢复和主界面。

### 2. 相关人员

- 产品决策与目标用户：当前提出需求的 NUCtool 用户。
- 工程实现与设备验收：项目维护者（姓名/设备型号待补）。
- 外部依赖：NUCtool.dll / EC-WMI / Windows powercfg；其行为需以当前打包版本、目标设备实测为准。

### 3. 背景

项目已有 EC 风扇、NUCtool.dll 性能预设和基准模式、Windows 电源管理、TDP、灯光、充电上限等功能。随着控制项增加，用户已明确表示难以判断功能归属；历史上还遇到硬件暂不可用、PowerShell 方案失败、灯光颜色不可选和长时间等待等情况。

现在有明确的控制规则可作为实现基线，但代码与文案仍留有“场景联动”和 DLL/Windows 计划混称。继续增加功能会扩大混乱范围，因此先完成控制可信度工作。

### 4. 目标与成功标准

**目标**：让用户能预测每个核心控件的影响范围，并用实际读回或准确的请求态反馈确认结果。

**首期验收指标（工程/设备测试指标，不代表已有产品分析数据）：**

- 所有核心设置都有唯一控制器标签；审计到的核心操作无未声明的跨控制器写入。
- 省电/平衡/性能分别请求 DLL profile 索引 3/2/1；实机支持的情况下读回索引与所选一致。
- profile 和 benchmark 操作的自动化测试证明没有调用 EC 风扇、风扇曲线或 TDP 写入。
- benchmark 只请求 DLL benchmark flag 与 vendor plan index 4；缺少回读时只显示“请求已发送/无法验证”。
- DLL vendor plan 与 Windows `powercfg` 在 UI 标签、命令和状态字段上完全分离。
- 注入任一子操作失败时，结果能指出失败项，界面不把组合结果显示为整体确认成功。
- 历史用户报告问题形成“复现 / 未复现 / 已解决 / 仍待查”记录，不将未复现问题算作已修复。

### 5. 用户与约束

- 主要用户：希望一键选择 DLL 原生性能档，并独立设置风扇曲线的 NUC 设备拥有者。
- 高级用户：会单独管理 Windows 电源计划、DLL 厂商计划、EC TDP、充电上限和键盘背光。
- 约束：没有可靠 benchmark/vendor plan 回读；键盘亮度也没有已验证回读。不同设备能力未由静态 DLL 导出表保证。未经实机验证，不承诺所有型号支持。

### 6. 价值

- 用户能放心点选，不担心性能档偷偷改变风扇或 Windows 计划。
- 遇到失败时能区分“未发送”“部分发送”“已读回确认”“无法读取”，减少猜测和重复操作。
- 工程排障可沿着单一控制器和明确子操作定位问题，降低未来功能维护成本。

### 7. 方案、范围与假设

#### 首期 Must

1. 移除“影视 / 游戏 / 基准”作为风扇与性能捆绑场景；风扇保留仅影响 EC 的曲线预设，DLL 性能另设省电 / 平衡 / 性能。
2. 基准模式作为独立 DLL 开关/计划，不调用 EC，不改变 EC 风扇曲线、接管状态或 TDP。
3. 为 DLL profile、DLL vendor plan、Windows `powercfg` 和 EC TDP 使用不同控件/字段/文案；profile 写入不顺带更改 vendor plan，除非用户明确在 vendor plan 控件操作。
4. 将每个组合操作的返回码拆分为子结果。能读回的字段展示实测值；不能读回的字段只显示最近请求状态。
5. 清查和处理旧 `apply_system_power_profile` 入口：明确所有写入副作用，拆分或撤下无法解释的复合路径。

#### 首期 Should

- 复现并处理用户报告的 TDP、系统电源方案、后端等待、灯光颜色问题；逐项附版本、设备和验证记录。
- 主界面控制项旁统一提供控制器与影响范围提示。
- 从普通操作页移除冗余操作日志；安全与错误诊断仍可用，后续单独定义留存和导出方式。

#### 暂不纳入

- 新增自动游戏识别、更多风扇控制器、未经验证的 DLL 导出、Aurora/灯条/RGB 新能力。
- 为了“完整”而混用旧 SDK fallback；若确需保留，应作为明示且独立的兼容路径评估。

#### 假设与待决事项

- DLL profile 3/2/1 分别代表省电/平衡/性能；索引标签须在目标 NUC 实机验证。
- 关闭 benchmark 后只清除 benchmark flag，还是恢复进入前的 profile 和 vendor plan，尚未决定。DLL 当前没有 benchmark/plan 回读；不得暗自宣称恢复成功。
- “取消日志”指移除普通用户可见的操作流水，不等于关闭内部安全/故障记录。
- 产品目前缺少用户量和使用数据；后续优先从支持工单/自愿诊断反馈获取证据，不虚构市场指标。

### 8. 分阶段发布

- **阶段 A：产品契约与调用映射**：完成本审计发现的 P0/P1 决策，确定命令/回读/文案映射。
- **阶段 B：核心边界修正**：拆分 EC 与 DLL 模式；拆开 profile、vendor plan、Windows 计划；补部分失败语义。
- **阶段 C：设备验证与可恢复性**：在目标型号验证读回、异常、重启、接管状态和失败后行为；历史故障逐项复现。
- **阶段 D：界面精简与发布材料**：按稳定的控制模型重排导航，保留用户需要的诊断说明，制作支持矩阵和发布说明。

不设日历日期；每阶段以验收项通过为完成条件。未完成目标设备验证前，只能标记“代码实现完成/未实机验证”，不得标记为设备兼容已确认。

## 用户故事与验收条件

### US-01：独立选择 DLL 性能档

**描述：**作为 NUC 用户，我希望直接选择省电、平衡或性能档，以使用 DLL 的原生性能模式，同时保持 EC 风扇设置独立。

- 省电 / 平衡 / 性能分别请求 DLL profile 3 / 2 / 1。
- 点击性能档不调用 EC 风扇、曲线、接管或 TDP 写入，也不修改 Windows 计划。
- profile 请求不隐式写 DLL vendor plan；页面分别显示两种状态。
- 有效回读与所选索引一致才显示“硬件已确认”；否则说明请求态或不匹配。
- DLL 不可用、返回错误或读回失败时，选择态不能伪装成当前硬件档位。

### US-02：独立调整 EC 风扇

**描述：**作为用户，我希望调风扇时只改变 EC 风扇控制，不影响 DLL 性能。

- 风扇区所有曲线、恒速、接管操作均走既有 EC 路径。
- 风扇曲线预设只影响 EC 参数，不触发 DLL profile、benchmark 或 vendor plan。
- 无 EC 连接或写入失败时，明确显示 EC 状态与失败项；不显示“运行中”。
- 性能页和风扇页使用不同的当前状态字段，不通过一个“场景”字段互相覆盖。

### US-03：独立 DLL 基准模式

**描述：**作为高级用户，我希望单独开关 DLL 基准模式，知道它不会更改 EC 风扇。

- 开启时只请求 DLL benchmark flag=1 和 vendor plan index 4；不调用 EC/TDP/Windows `powercfg`。
- 关闭时至少清除 DLL benchmark flag；如果还原 profile/plan 的策略未定，不显示“已恢复”。
- 无 benchmark/plan 回读时，界面标为“最近请求/无法读取”，不显示“硬件已确认开启”。
- 部分调用失败会指出具体失败子项。

### US-04：区分厂商计划和 Windows 计划

**描述：**作为用户，我希望知道 DLL vendor plan 和 Windows 电源方案不是同一设置。

- DLL `wcf_set_power_plan` 区域标为“NUCtool 厂商电源计划（DLL）”。
- Windows `powercfg` 控件只操作 Windows 电源 scheme/对应系统参数，不能触发 DLL plan 或 Uniwill/NVIDIA 等未提示操作。
- 两者拥有独立读写状态；没有回读的一方不显示为“当前已确认”。
- 所有旧复合命令的影响范围在产品文案和测试清单中可追踪。

### US-05：理解真实状态与失败

**描述：**作为用户，我希望分清真实读回、请求已发和无法读取。

- 每个关键值的状态标记为“硬件读回”“最近请求”“不可用/无法读取”之一。
- 组合操作逐项汇总，不因某个字段回读成功就把其它字段都显示成功。
- 故障提示包含控制器、操作阶段、可读错误原因和一个安全的下一步建议。
- 后端长时间未返回时显示当前等待阶段，并在定义的超时策略后提供重试/取消或恢复提示；不能无限显示模糊等待态。

### US-06：精简普通日志但保留必要诊断

**描述：**作为普通用户，我希望主控制界面简洁，同时在硬件出错时仍可排查。

- 默认主界面不展示冗长操作流水。
- 风扇安全告警、控制失败和最小必要诊断不因隐藏 UI 日志而消失。
- 若支持导出/清理诊断，说明内容类别、位置及用户操作方式；不写入未经确认的个人数据。

## 发布前验证门槛

1. 单元/集成测试对 DLL/EC/Windows 命令路由做断言，验证每个入口只写入其声明控制器。
2. 注入连接失败、单个 DLL 返回失败、读回失败、EC 不可用和超时，验证部分失败状态。
3. 在指定目标 NUC 型号上记录每个关键操作的写前状态、请求索引/数值、返回码、写后读回和重启后状态。
4. 人工检查 UI 标签与 Tauri 实际命令对应；重点检查所有“Windows 电源计划”文案、profile/plan 联动和“已确认”文案。
5. 历史报错逐项登记复现结论；未在目标设备复现的条目保持“待验证”，不做已修复声明。
